# Skill Creator —— 从 0 到 1 编写 Skill

## 前置条件

开始编写 SKILL.md 之前，确认：

1. **项目目录已存在**：`<skill-factory>/<skill-name>/` 已创建
2. **安装模式已确定**：直链或构建已选定
3. **发布映射已注册**：`publish.map` 已添加条目
4. **软链已创建**：对应 agent 的 skills 目录已有软链

任何一项未完成，先引导用户用 `skill-bootstrap` 完成初始化。

---

## 核心流程

```
捕获意图 → 访谈细化 → 编写初稿 → 测试验证 → 迭代改进 → 优化触发描述
```

### 第一步：捕获意图

理解用户到底想让这个 Skill 做什么。当前对话可能已经包含了一个用户想固化的工作流（比如用户说"把这个流程做成 Skill"）。如果是，先从对话历史中提取——用到了哪些工具、步骤顺序、用户做了哪些修正。

需要明确的四个问题：

1. **这个 Skill 要让 AI 做什么？** — 核心能力
2. **什么时候应该触发？** — 用户会说什么话、在什么场景下
3. **预期的输出是什么格式？** — 文件、对话、结构化数据
4. **需要测试用例吗？** — 有客观可验证输出的 Skill 适合测试；主观输出的（写作风格、创意类）通常不需要

#### 经验驱动设计（Evidence-Based Design）

当 Skill 的意图来自一段**真实的实践经历**（一个长 session 中反复试错、修正、迭代出的工作流），仅靠"访谈"不够——需要从实践中提炼：

**1. 回顾 Session 轨迹**：读取 session 记录，提取完整时间线、所有错误和恢复、所有用户纠正（"不要这样"/"应该这样"）、所有过程决策（为什么选 A 不选 B）。

**2. 审计现有产物**：检查实践中产出的所有文件——目录结构是否完整？文件之间是否一致？有无孤立产物？

**3. 挖掘本地工作**：扫描实践中产出的领域知识——分析报告、工程洞见、性能报告、代码审查、设计文档。（去你实际产出知识的地方找。）

**4. 综合设计**：基于以上来源，输出问题清单（按严重度）、红线清单（来自用户纠正）、标准输出格式、知识来源映射、覆盖追踪机制。这些直接映射到 SKILL.md 的 Red Lines、Standard Output、References 等章节。

**判断标准**：如果用户说"回顾一下我们刚才做的整个过程"、"把我们踩的坑都沉淀下来"、"从这次经历中提炼一个 Skill"——走经验驱动设计，不走纯访谈。

### 第二步：访谈细化

主动追问边界情况、输入输出格式、成功标准、依赖项。不要急着写——先把需求理清楚。调研是否已有类似功能的 Skill，避免重复建设。

### 第三步：编写 SKILL.md

#### YAML Frontmatter（必须）

```yaml
---
name: my-skill-name
description: [触发描述——什么时候用、做什么。要具体，要"积极"一些]
---
```

**description 的写法很关键**——它是 AI 决定是否读取这个 Skill 的唯一依据。

- ❌ 差：`"数据可视化工具"`（太模糊，AI 不知道什么时候该用）
- ✅ 好：`"数据可视化与 Dashboard 构建。当用户提到仪表盘、数据图表、指标展示、'做个报表'、'画个图'时触发，即使用户没有明确说'dashboard'。"`

写 description 时要偏"积极"——当前 AI 倾向于少触发而不是多触发，所以宁可多列触发场景。

#### 正文结构

```markdown
# [Skill 名称] —— 一句话定位

## 角色定义 / 概述
你是什么，你负责什么

## 触发场景
列出具体的触发条件（补充 description）

## 核心流程 / 工作模式
主要工作流程，用步骤或流程图表达

## 输出规范
输出的格式、结构、存储位置

## 关键原则 / 行为约束
做什么、不做什么

## 与其他 Skill 的协作（如有）
上下游关系
```

#### 渐进式披露

Skill 的信息分三层加载：

| 层级 | 内容 | 何时加载 | 建议大小 |
|------|------|---------|---------|
| **元数据** | name + description | 始终在上下文 | ~100 词 |
| **正文** | SKILL.md 全文 | Skill 被触发时 | <500 行 |
| **参考文档** | references/ 下的文件 | 按需读取 | 不限 |

**关键原则**：
- SKILL.md 控制在 500 行以内；接近上限就把详细内容拆到 `references/`，正文只留指引
- 大的参考文件（>300 行）要加目录
- 多领域/多框架的 Skill，按领域拆分参考文件，AI 只读需要的那个

**拆分判断**：只有当 Skill 存在**多条不同的使用路径**、且每条路径只需参考文档的一个子集时，才值得拆到 references/。如果每次调用都需要全部内容，保持单个 REFERENCE.md 反而更直接。SKILL.md 中的导航表应写成条件路由（"做 X 时读 A，做 Y 时读 B"），而非全量 checklist。

#### 写作风格

- **解释"为什么"而不是堆"必须"**：当代 LLM 很聪明，理解了动机就能灵活应对。如果你发现自己在写 ALWAYS 或 NEVER（全大写），这是个黄旗——试着换成解释原因的方式
- **用命令式语气**写指令（"扫描目录结构"而不是"你应该扫描目录结构"）
- **写通用的，不要写死在特定例子上**：Skill 会被反复使用，不要为某个特定场景过度拟合
- **写完初稿后，换个视角重新审视一遍再改进**

### 第四步：测试验证

写完初稿后，设计 2-3 个真实的测试提示词——用户真的会说的话。和用户确认这些测试用例是否合理，然后实际运行：读取 SKILL.md，按指令完成测试提示词的任务，再和用户一起评估结果。

### 第五步：迭代改进

1. **从反馈中泛化**：不要为修某个测试用例的问题而做过于特化的修改。想想这个问题在更多场景下意味着什么，做通用性改进
2. **保持精简**：删掉没有发挥作用的指令
3. **解释原因**：把"为什么这样做"传递给 AI，比写死"必须这样做"更有效、更灵活
4. **提取重复模式**：如果多次测试中 AI 都独立写了类似的辅助代码，说明应该把它打包成 `scripts/` 下的脚本

持续迭代直到：用户满意、测试用例全部通过、改进已经收敛。

### 第六步：优化触发描述（可选）

1. 列出 10 个"应该触发"的用户输入（不同表述、正式/口语混合、含边界情况）
2. 列出 10 个"不应该触发"的用户输入（关键词接近但实际是不同需求的"近似" case）
3. 在脑中模拟：如果 AI 只看到 description，能正确判断吗？
4. 调整 description 直到覆盖所有应触发的场景，同时排除不应触发的

**好的"不触发"用例不是明显无关的**（给 PDF Skill 写"写个斐波那契函数"太简单了）。好的"不触发"用例是那些关键词相近但需求不同的近似场景。

## 与其他元 Skill 的关系

```
skill-bootstrap  →  项目结构初始化（在哪做、怎么发布）
       ↓ 项目就绪
skill-creator    →  SKILL.md 内容编写（怎么写好）  ← 本 Skill
       ↓ 初版完成
skill-iterating  →  持续迭代优化（从 1 到 N）
```
